## Summary

The course concludes with product demonstrations, a shared review, and preparation for the oral examination. The suggested exam structure covers the elevator pitch, customer value, the role and limitations of AI, architecture and data flow, development method, portfolio reflections, individual contribution, security, quality, and next steps.

Explaining a system reveals whether its design is understood beyond the code. The examination connects technical choices to the original problem and asks where AI adds value, where it can fail, and where human approval is necessary. It also makes the development process and personal contribution visible.

## Suggested examination structure

The course guide groups preparation into seven areas:

1. **Elevator pitch:** what was built, who it serves, and which need it addresses.
2. **Project and value:** the customer's problem, the expected benefit, project assumptions, and deliberate exclusions.
3. **AI component:** where AI appears, its input and output, why it is appropriate, where it can fail, and where human approval belongs.
4. **Technical solution:** frontend, backend, database, data flow, API calls, error handling, response time, uncertainty, and deployment.
5. **Portfolio reflection:** the course ideas that influenced the project and how the understanding of AI development changed.
6. **Individual contribution:** personally implemented work, understood components, decisions, and learning.
7. **Perspective:** required testing, the greatest risk, the next product step, and the most important lesson from the course.

## Topics to revisit

The preparation material recommends being ready to connect the following terms to the project:

- RAG, embeddings, chunking, vector databases, retrieval, and prompt engineering.
- System prompts, user prompts, tokens, structured output, bias, and hallucinations.
- LLM API integration, timeouts, invalid responses, and error handling.
- Code agents and the difference between a one-off prompt and an agentic workflow.
- Spec-driven development, requirements, decisions, tickets, and change logs.
- Prompt injection, secret management, `.env` files, and other security choices.

## Key takeaways

A project should be explainable at several levels: a short purpose statement, a user and value story, a system architecture, and a detailed account of important decisions. RAG, prompts, APIs, agents, specifications, safety, ethics, testing, and limitations should be discussed in relation to the actual project rather than as isolated definitions.

- Support claims with examples from the working product or development history.
- Explain important trade-offs instead of listing technologies.
- Be specific about personal work within the team result.
- Describe limitations honestly and pair them with a sensible next step.

## Closing note

The strongest final presentation is not the one that claims the project is perfect. It is the one that demonstrates a useful result, explains why the system is built as it is, and shows enough critical distance to identify risks and a realistic next step.
