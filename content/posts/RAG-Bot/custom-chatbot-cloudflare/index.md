The first version of the portfolio chatbot used Dify's standard embedded widget. It
proved that retrieval worked, but the interface did not feel like part of the site. Its
visual style, layout, and interaction were controlled by the embed, and connecting to
Dify directly from custom browser code would have exposed the private application API
key.

The production version therefore uses a **custom chat interface backed by a Cloudflare
Worker**. The browser owns the presentation, Dify still handles retrieval and answer
generation, and the Worker is the secure boundary between them.

## Architecture

```text
Visitor
  ↓
Custom portfolio chat panel
  ↓  POST /chat
Cloudflare Worker
  ↓  authenticated streaming request
Dify chat application
  ↓
Portfolio knowledge base
```

The responsibilities are intentionally separated:

- **Hugo** renders the chatbot markup and a map between Dify document names and public
  portfolio URLs.
- **Browser JavaScript** opens the panel, locks background scrolling, sends questions,
  reads the streamed response, and renders citation links.
- **Cloudflare Worker** validates the browser request, adds the private Dify credential,
  and forwards Dify's server-sent event stream without buffering it.
- **Dify** retrieves relevant portfolio chunks and generates an answer grounded in that
  context.
- **GitHub Actions** synchronizes Markdown content into the Dify knowledge base when the
  source content changes.

## Why the Worker is necessary

A Dify application API key must not be shipped in HTML or JavaScript. Anything sent to
the browser can be inspected, regardless of whether the code is minified or the value is
called an environment variable.

The Worker stores the key as an encrypted Cloudflare secret:

```sh
npx wrangler secret put DIFY_API_KEY
```

Only the Worker can read that value. The public site calls the Worker endpoint, and the
Worker adds the `Authorization: Bearer ...` header when it calls Dify. The secret is not
committed to Git, included in Hugo's generated files, or returned to the visitor.

The Dify **chat application key** stored in the Worker is also separate from the
**dataset key** used by the content-sync workflow. Keeping those credentials separate
limits what each part of the system can do.

## Request validation and CORS

The Worker exposes `/chat` and `/api/chat`. Before contacting Dify it checks:

- the request origin against the configured production and local-development origins;
- that the method is `POST` (with `OPTIONS` supported for CORS preflight);
- that the JSON body and question stay within size limits; and
- that conversation and user identifiers contain only expected characters.

Allowed origins are configured in `cloudflare-worker/wrangler.toml`. The GitHub Pages
origin is the domain only—`https://dannyshayh.github.io`—even though the portfolio is
served below `/Portfolio/`.

These checks prevent accidental cross-site use through a normal browser. They are not a
complete replacement for rate limiting, because a non-browser client can forge an
`Origin` header. A Cloudflare rate-limit or WAF rule is the appropriate additional layer
if traffic grows.

## Keeping the answer streamed

The Worker requests Dify's `streaming` response mode and returns the upstream body as an
`text/event-stream` response. It also sets `X-Accel-Buffering: no` and disables caching.
That lets the custom interface display the answer as it arrives instead of waiting for
the whole model response.

The browser processes Dify events incrementally:

- `message` and `agent_message` append answer text;
- `message_replace` replaces the current draft when Dify revises it;
- `message_end` supplies the final retrieval metadata; and
- `error` becomes a readable message inside the chat panel.

Generated `Answer:` and `Sources:` wrappers are removed continuously rather than only at
the end. This prevents the visible response from suddenly changing when streaming
finishes.

## Turning retrieval metadata into citations

Dify returns `retriever_resources` at the end of a grounded answer. Each resource uses
the stable document name generated by `upload_to_dify.py`, for example:

```text
portfolio__posts__RAG-Bot___index.md
```

During the Hugo build, `layouts/partials/chatbot.html` creates a JSON map from those
document names to the corresponding page title and relative URL. The frontend matches
the retrieval metadata against that map, removes duplicate pages, and renders the result
inside a **View citations** dropdown.

This keeps URLs out of the model prompt and makes the links deterministic. A citation
opens the real portfolio page even if the model describes the source differently in its
answer.

## Custom interface behaviour

The custom panel lives in `layouts/partials/chatbot.html`, its behaviour is in
`assets/js/chatbot.js`, and the visual treatment is in `assets/css/custom.css`. It adds
features that were difficult to control in the embedded widget:

- a peach launcher and dark styling that match the portfolio;
- streamed responses in the existing visual language;
- quick questions with retrieval-focused prompts;
- an expandable citation list with internal links;
- a reset action for starting a fresh Dify conversation;
- responsive sizing for mobile screens; and
- complete background scroll locking while the panel is open.

The scroll lock also resets during `pagehide` and `pageshow`. That matters when a visitor
follows a citation and then uses the browser's Back button: without cleanup, the browser
can restore a page from its back-forward cache while the body is still fixed in place.

## Deployment flow

The Worker is deployed independently from the static Hugo site:

```sh
cd cloudflare-worker
npx wrangler deploy
```

Hugo only needs the public Worker URL in its chatbot configuration. Content updates do
not require redeploying the Worker. Instead, the knowledge-sync workflow updates Dify
when files under `content/` change, while normal interface changes use the regular
GitHub Pages build.

## What I learned

Replacing an embed is not only a styling task. It means taking responsibility for secret
management, input validation, CORS, streaming event parsing, conversation state,
accessibility, mobile behaviour, navigation cleanup, and traceable sources.

The Worker remains deliberately small: it does not generate answers or duplicate the
retrieval pipeline. It protects the credential and transports the stream. Keeping that
boundary narrow made the custom experience possible without turning the static
portfolio into a separate backend application.
